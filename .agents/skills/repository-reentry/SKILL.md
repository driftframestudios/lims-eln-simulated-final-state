# Simulation repository re-entry

## Contract

- **What:** A repository-local method for recovering settled, current, open,
  and next Simulation state.
- **When:** Work resumes after a handoff, a branch or pull request changes, or
  source, orientation, release, constellation, and comparison records appear
  to disagree.
- **Boundaries:** Runnable source and tests define current behavior. The signed
  tag, promotion receipt, and retained release bundle define accepted release
  standing. The release remains immutable while living orientation records
  advance to support re-entry. Change and production authority remain with
  their named owners.
- **Result:** One authoritative source path, one live collaboration surface,
  the material difference among records, and one bounded next move.

## Rules

### Rule: Current source and accepted forecast answer different questions

Read the working branch to establish current behavior. Read the promotion
receipt, signed tag object, commit, tree, archive, and retained bundle to
establish released standing. A later `develop` correction can improve living
orientation while the accepted `main` release remains unchanged.

### Rule: The living re-entry carriers have distinct jobs

Use `machine-node.json` for repository identity and authority posture,
`first-receipt.json` for compact selected-future state and handoff,
`COORDINATION-HORIZON.json` for current work and entry signals, and
`constellation.lock.json` for exact sibling coordinates and declared semantic
relations. Name a stale carrier instead of blending its earlier state into the
current account.

### Rule: Simulated, observed, and accepted states remain distinct

The executable selected future can be complete on its own terms. Environment
observation remains a separate evidence route. A comparator admits an accepted
coordinate while simulated evidence retains its declared mode and accountable
production roles retain authorization.

### Rule: Branch topology remains visible

Ordinary work begins from `develop`. A release branch assembles one candidate
for `main`; an accepted hotfix begins from `main` and returns forward to
`develop`. Read the live pull request before treating a local branch name as the
receiving route.

### Rule: Existing work retains its owner

Inspect the worktree before editing. Preserve unrelated changes, and route an
overlap to its current owner when files cannot be changed independently.

## Operating sequence

1. **Recover Git state:** Run `git status --short --branch`, refresh relevant
   remote references, and inspect recent `main`, `develop`, and active-branch
   history.
2. **Read orientation:** Read `README.md`, `AGENTS.md`, the release role,
   Machine Node, First Receipt, Coordination Horizon, and constellation lock.
3. **Resolve the live receiver:** Read the related Issue or pull request when
   its status, review, or ownership affects continuation.
4. **Inspect the material owner:** Read the exact assumption, fixture, runtime
   source, schema, retained artifact, validator, workflow, or release record
   that owns the behavior in question.
5. **State the difference:** Separate accepted release state, current source,
   living coordination, open evidence, and the next receiver.
6. **Choose one move:** Select the smallest source-owned action and the exact
   check that can establish its result.
