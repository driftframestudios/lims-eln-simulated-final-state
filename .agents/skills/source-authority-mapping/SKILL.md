# Simulation source authority mapping

## Contract

- **What:** A repository-local method for tracing one material Simulation
  object from the source that defines it to the receiver that can act on it.
- **When:** Assumptions, specification, executable source, generated artifacts,
  deterministic replay, retained closure, release acceptance, or independent
  comparison could be treated as the same authority.
- **Boundaries:** The map records evidenced relations and granted decisions.
  It preserves simulation scope, publication, privacy, license, attribution,
  and production-authorization boundaries. Accepted Simulation source retains
  semantic authority when delivery and comparison carriers receive it.
- **Result:** A concise lineage map naming the material object, authority roles,
  typed relations, exact coordinates, current receiver, evidence limit, and
  event that reopens the map.

## Rules

### Rule: Begin with one material object and decision

Name the claim, assumption, fixture, operation, output, receipt, closure, or
coordinate and the decision its route should make possible. A repository
inventory is useful only when it changes that route.

### Rule: Keep authority roles independent

Distinguish the roles that matter:

- intended meaning and selected-future assumption;
- synthetic fixture or database-oracle input;
- executable runtime source;
- generated artifact and strict parser;
- deterministic replay and validator;
- retained release bundle;
- signed release acceptance; and
- independent comparison and accountable environment observation.

One file or repository can carry several roles. Record each role instead of
collapsing them into a general owner label.

### Rule: Type every decision-changing relation

Use literal relations such as `defines`, `constrains`, `executes`, `generates`,
`validates`, `retains`, `accepts`, `compares`, or `observes`. A comparator
consumes an accepted coordinate while Simulation retains authority for the
selected future.

### Rule: Identity, evidence mode, and retrieval remain separate

A stable future-reality identity can remain constant while a branch, source
commit, tag, or retrieval route changes. Record stable identity, evidence mode,
accepted revision, and retrieval route as separate facts.

### Rule: Promotion carries exact coordinates

When a receiver adopts Simulation material, retain the signed tag object,
peeled commit, tree, reproducible archive digest, retained bundle digest,
relation, and evidence posture needed for later reconciliation. A floating
branch can support exploration while governed comparison uses accepted
coordinates.

### Rule: End at a capable receiver

Name the source file, repository, workflow, comparator, or accountable role
that can make the next decision. Preserve what current evidence establishes and
which claim remains with another observation.

## Operating sequence

1. **Name the object and decision.**
2. **Locate meaning and inputs:** Read the selected-future statement,
   assumptions, intended-use profile, fixtures, and database oracle that apply.
3. **Locate execution and evidence:** Read runtime source, generated artifacts,
   parsers, validators, focused tests, and retained closure.
4. **Resolve acceptance and receiving use:** Read the promotion receipt,
   release coordinate, constellation lock, and comparison route when they
   affect the decision.
5. **Trace typed relations:** Follow only sources and receivers that change the
   decision.
6. **Select the route:** Keep, correct, regenerate, compare, defer, form a
   successor, or return a question to the named steward.
7. **Preserve re-entry:** Record exact source, coordinate, evidence boundary,
   and condition for renewed reconciliation.

next, and which change would reopen reconciliation.
