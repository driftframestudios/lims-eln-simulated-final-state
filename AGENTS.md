This repository owns one executable selected future for the LIMS/ELN program.
Make changes here when simulated behavior, its declared assumptions, retained
artifacts, release evidence, or the living comparison route needs to change.

## Keep authority and evidence roles distinct

- This repository can be definitive inside its declared future reality.
  Production authorization remains with the accountable production roles.
- Synthetic fixtures, assumptions, executable source, and the database oracle
  define the simulated inputs and behavior.
- Generated outputs and two-run byte comparison establish deterministic replay
  for the named source and inputs.
- The retained bundle and signed release coordinate establish the accepted
  Simulation baseline.
- Environment observations remain separate evidence. Comparative Evidence owns
  their admission and difference classification against accepted coordinates.
- A change to selected-future meaning forms a successor identity and release;
  living orientation corrections can advance independently when retained bytes
  and signed release truth remain unchanged.

## Use the accepted branch route

- `main` contains released forecast baselines; `develop` integrates the next
  forecast.
- Begin bounded work from `develop` on `feature/`, `fix/`, or `chore/`, then
  return it to `develop` through review.
- Form `release/<semver>` when one candidate freezes comparison inputs. Form a
  `hotfix/` from `main` for an accepted release repair, then merge the accepted
  correction forward into `develop`.
- Keep historical and selected-future tags immutable so later comparisons can
  recover what the team accepted at that time.

## Write toward the verifiable state

- Lead with the behavior a collaborator can create or verify.
- Pair a safety, privacy, scope, or authority boundary with the affirmative
  behavior that keeps the simulation useful.
- Use ordinary language around exact technical and regulated terms. Define
  repository shorthand where it first changes a reader's decision.
- State what each observation establishes before its coverage boundary.
- Keep personal attribution in the repository's approved carriers. Commit,
  Issue, pull-request, and review prose stays focused on the change.

## Validate the material behavior

Use a configured Python 3.12 interpreter for the complete source-owned proof.
The examples below assume `python3` resolves to that interpreter:

```sh
python3 -m unittest discover -s tests -v
python3 tools/validate_repository.py
python3 tools/verify_release_coordinate.py
git diff --check
```

The aggregate validator regenerates the selected future twice in isolated
directories, parses strict JSON, compares the complete artifact inventory and
bytes, checks the retained bundle and living bindings, and scans repository
text for credential-shaped values. The release verifier independently checks
the signed tag subject, commit, tree, archive, receipt, and trusted signer.
